## Diseño y arquitectura

`ShellForm` contiene cuatro regiones permanentes: menú lateral, encabezado, área central desplazable y pie de estado. La navegación sustituye y dispone solo los controles de la página anterior, dentro del mismo formulario. Los botones laterales son botones WinForms reales, con nombre accesible, foco de teclado y descripción de selección. Los iconos se dibujan con líneas; no dependen de glifos de una fuente especial.

Tema oscuro, Segoe UI, bordes discretos y acento ámbar inspirado en los ojos del logotipo. La selección se reconoce por fondo, texto e indicador lateral. `Surface`, `Tile`, `TileGrid` y `VStack` separan las piezas de presentación: las tarjetas se redistribuyen en una, dos o tres columnas; las etiquetas se miden según el ancho disponible y crecen para envolver el texto. Las páginas se desplazan verticalmente; el menú puede desplazarse por separado cuando falta altura.

Los botones de operación dicen **«Sin conectar»** y tienen `Enabled=false`; no tienen manejadores que invoquen módulos. «Explorar herramientas» solo navega a Rendimiento. No se importan los módulos de v0.8.1. No hay proveedor CIM/Storage/Appx, consulta de Registro, enumeración de procesos, consulta de energía ni lectura de respaldos. Las únicas lecturas propias de la vista son el código/ícono locales y las métricas necesarias del monitor/DPI/controles.

### Escala y tamaños

El proceso independiente solicita conciencia DPI de sistema mediante `SetProcessDPIAware` antes de crear controles. Usa **una sola estrategia de medidas**: coordenadas lógicas multiplicadas por el DPI inicial y fuentes Segoe UI en puntos; `AutoScaleMode.None` evita un segundo escalado automático. Los elementos creados al navegar usan la misma escala. No se altera el DPI de Windows, el Registro, el manifiesto ni `powershell.exe.config`.

Al abrir se limita el tamaño al área útil del monitor; es posible redimensionar/maximizar y usar scroll. En áreas pequeñas el menú reserva el ancho de su barra vertical para no crear una barra horizontal accidental. Las tarjetas calculan columnas según el espacio disponible y las etiquetas ajustan su altura. El pie usa puntos suspensivos si falta ancho; no contiene acciones necesarias para navegar.

Esta estrategia es **system-aware**, no PerMonitorV2. Cambiar el DPI durante la sesión o mover entre monitores de distinta escala puede producir escalado de mapa de bits y requiere validación real. Si el host ya fijó su conciencia DPI, Windows puede conservarla; se debe usar el lanzador en un proceso nuevo. Microsoft documenta estas diferencias en [DPI del proceso](https://learn.microsoft.com/en-us/windows/win32/hidpi/setting-the-default-dpi-awareness-for-a-process) y [DPI de WinForms en .NET Framework](https://learn.microsoft.com/en-us/dotnet/desktop/winforms/high-dpi-support-in-windows-forms?view=netframeworkdesktop-4.8).

## Cómo verlo

1. Abrir `C:\GitHub\Juno\Abrir-Juno-Prototipo.cmd` como usuario normal. La entrada estable sigue siendo `Abrir-Juno.cmd`.
2. Recorrer las seis secciones desde el menú. Probar también «Explorar herramientas». No deben abrirse diálogos de módulos.
3. Reducir la ventana y verificar el cambio a una columna y el scroll del contenido y del menú. Maximizar para consultar las tarjetas del dashboard.
4. Recorrer con Tab y activar la navegación con Espacio/Enter. Los botones «Sin conectar» permanecen inactivos. El enlace de Acerca de, si se pulsa, abre el navegador.
5. Cerrar con la X y volver a abrir. No se solicitan privilegios administrativos ni se guardan preferencias.

Si falla el lanzador, abrir Windows PowerShell 5.1 y ejecutar:

```powershell
powershell.exe -NoProfile -STA -ExecutionPolicy Bypass -File "C:\GitHub\Juno\Juno-Prototipo.ps1"
```

Bypass afecta únicamente al proceso lanzado. No modifica la política persistente. No hace falta instalar PowerShell 7.

## Verificación

Resultado final: **366/366 pruebas aprobadas en x64 y 366/366 en x86**, con Windows PowerShell **5.1.22621.6133** y Pester **3.4.0**. Cada ejecución conserva las **338 pruebas de v0.8.1** y añade **28 del prototipo** (732 ejecuciones en total). El C# se compiló con el compilador nativo de .NET Framework en ambas arquitecturas. Los **21 scripts PowerShell** se analizaron sin errores de sintaxis en x86/x64. `git diff --check` limpio; también se revisaron espacios finales en los archivos nuevos. No se modificó ningún archivo estable y el índice sigue vacío.

Las pruebas nuevas comprueban las seis rutas, la única selección, el botón de explorar, la ausencia de ventanas secundarias, la inactividad de las operaciones y el enlace exacto sin abrir el navegador. Se construyen todas las páginas a 1180×790, 940×650 y 700×500 de cliente y se comprueba geometría de hermanos, contención y altura de etiquetas. Se ejercitan los puntos de cambio de columnas con factores lógicos 1/1,25/1,5/2; esto no sustituye una sesión gráfica con esos DPI.

Un proceso hijo de la misma arquitectura usa el bucle real `Application.Run`, eventos `Shown`/`FormClosed` y un timer de prueba: abre la ventana, recorre las seis secciones, comprueba desplazamiento y reinicio al navegar, cierra y dispone recursos. Solo actúa sobre su propio formulario. Se verifican también recursos opcionales ausentes, navegación repetida que dispone la página anterior y disposición idempotente. Las guardas de código revisan que el shell no importe motores ni use proveedores/escritores de configuración; `Process.Start` solo existe para el URL fijo de GitHub.

La automatización del escritorio no devolvió una ventana seleccionable de este host PowerShell. Por ello, la revisión visual se hizo sobre renders nativos y las aperturas/cierres se verificaron con el proceso de prueba. No se atribuye una prueba manual de escritorio ni una matriz Windows 10/11 a esa evidencia. Los procesos temporales del prototipo se cerraron al terminar la comprobación.

## Problemas detectados y resueltos

- Tipado del badge del encabezado: se corrigió durante la compilación nativa para usar `Label`.
- Iconos que se estiraban al ancho completo de las tarjetas: se conserva su ancho propio en el contenedor vertical.
- Encabezado sin distribuir antes del primer reajuste y poco espacio entre marca/versión: se fuerza el layout inicial y se separan las etiquetas; el badge pasa a segunda línea en ventanas estrechas.
- Barra horizontal lateral al aparecer el scroll vertical: los botones calculan su ancho usando el área cliente disponible; hay una prueba específica.
- Se evitó mezclar escalado manual con automático para que las páginas creadas después de abrir usen la misma estrategia.

No se detectó una regresión que requiriese modificar la lógica estable durante esta etapa.

## Integración posterior, después de aprobar el diseño

1. Introducir un catálogo de herramientas con identificadores de operación únicos, capacidades, estado y comando; separar esos identificadores de los nombres de los iconos. Las tarjetas reciben ese catálogo en vez de conectar acciones por el texto visible.
2. Sustituir el contenido de demostración por un proveedor de instantáneas de solo lectura. El trabajo lento debe ejecutarse fuera del hilo de UI y devolver DTOs; solo el hilo de UI actualiza controles. Definir tiempo de espera, cancelación y estados parcial/desconocido antes de conectar consultas.
3. Crear adaptadores PowerShell hacia las funciones existentes de v0.8.1, conservando mutex, ámbito de usuario/equipo, originales, diarios, elegibilidad y revalidaciones. No copiar esas implementaciones a C# ni implementar un segundo motor de restauración.
4. Convertir gradualmente los diálogos actuales en vistas insertables con propiedad explícita de recursos. Mantener separadas consulta, solicitud, confirmación, escritura y eficacia. No activar un botón hasta que su adaptador y sus guardas estén probados.
5. Ejecutar primero navegación/lectura en las ediciones reales y después, con autorización separada, las pruebas de modificación/restauración. Este prototipo no modifica la coordinación entre instancias de la versión estable.

## Límites y revisión pendiente

Se conservan valores demo y acciones inactivas. No hay sesiones, persistencia de preferencias, trabajos en segundo plano, integración con respaldos ni protección de instancia del motor: cada prototipo es una ventana visual independiente. Se necesita aprobar el diseño antes de conectar funciones.

Pendientes: Windows 10/11 Home/Pro reales, DPI 100/125/150/200 % con fuentes reales y monitores mixtos, fuentes de accesibilidad, alto contraste y lector de pantalla. Los controles mantienen nombres, foco y navegación de teclado básicos, pero eso no certifica accesibilidad. Las capturas y pruebas geométricas no prueban todos los cambios de tema, fuentes ni efectos del escritorio.

Los cambios quedan sin stage y sin commit para revisión. El trabajo se detiene aquí.
