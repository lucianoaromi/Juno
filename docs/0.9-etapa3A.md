# JUNO v0.9 — Etapa 3A: Transparencia de Windows

Fecha: 18/10/2026. Rama: `feature/juno-ui-0.9`.

## Resultado y alcance

El dashboard mantiene sus cinco categorías, actualización manual y trabajador lector. Restauración indica expresamente que la recuperación general aún no está integrada y remite la transparencia a Rendimiento. Se conservan tema, distribución, icono y tecnología.

**No se realizaron cambios reales de transparencia, restauraciones, notificaciones al escritorio, optimizaciones ni modificaciones de configuración de Windows durante esta etapa.** Las escrituras de prueba se limitaron a objetos ficticios y archivos privados de TestDrive. ## Arquitectura de integración

```text
Juno-Prototipo.ps1
  → ShellForm / TransparencyController
      → ITransparencyService / PowerShellTransparencyService
          → Task fuera del hilo UI
              → runspace privado STA (ReuseThread)
                  → TransparencyAdapter.ps1
                      → Enter-JunoLease
                      → estado + validación del respaldo
                      → Set-Transparency / Restore-Transparency
                          → Invoke-JunoTransparency (motor estable)
                          → BackupStore / diario / frontera Windows
                      → nueva lectura y resultado
                      → Exit-JunoLease (finally)
      ← timer WinForms recoge resultados / revisiones
```

El constructor del proveedor no consulta ni importa motores. `LoadOnly` solo compila los tipos. Inicio abre el dashboard lector; la primera visita visible a Rendimiento inicia una consulta de transparencia. Después se actualiza mediante «Consultar estado» y al finalizar una operación. Navegar conserva el controlador y no inicia solicitudes superpuestas.

El puente acepta únicamente Read, Enable, Disable y Restore. Pasa argumentos estructurados al runspace, sin interpolarlos como código ni abrir otra GUI. Cada invocación adquiere, utiliza y libera el bloqueo desde el mismo hilo del runspace. La tarea de C# puede esperar sin bloquear el hilo de controles. No se reutiliza el trabajador de dashboard para escrituras.

La UI recoge resultados únicamente cuando la tarea terminó. Hay una operación de transparencia por controlador/proveedor. Durante una operación se deshabilitan los cuatro controles; la navegación continúa. El cierre normal espera si hay una escritura/restauración en curso. Cerrar durante una lectura dispone la vista y deja al proveedor terminar y liberar sus recursos, sin callbacks a controles destruidos. No se cancela una transacción a mitad de escritura.

### Revisiones históricas

La confirmación inicial usa un diálogo oscuro con acento dorado y Cancelar predeterminado. Si el motor estable requiere revisar un respaldo histórico, `Confirm-JunoReview` se adapta **solo dentro del runspace privado**: envía el texto original, incluidos Actual y Original, a la UI y espera la decisión conservando el mutex.

La UI pausa el timer durante el diálogo para evitar revisiones modales repetidas. Cada respuesta queda ligada a su revisión; una respuesta tardía no puede autorizar una solicitud posterior. Cancelar, cerrar el diálogo o disponer el proveedor rechaza una revisión pendiente. La disposición no detiene una escritura ya iniciada.

Referencias de implementación: [PSThreadOptions.ReuseThread](https://learn.microsoft.com/en-us/dotnet/api/system.management.automation.runspaces.psthreadoptions?view=powershellsdk-1.1.0) y [propiedad del Mutex](https://learn.microsoft.com/en-us/dotnet/api/system.threading.mutex?view=netframework-4.8.1). Se conserva la afinidad de hilo exigida por el almacén existente.

## Garantías de seguridad y significado de los estados

- **Ámbito:** solo HKCU del usuario que ejecuta JUNO. Se conserva `%LOCALAPPDATA%\WinRendimiento\backup.json`, Kind General, Scope User, identidad, revisión y validación completas. No se migra ni escribe el almacén de equipo.
- **Lectura:** abre `Software\Microsoft\Windows\CurrentVersion\Themes\Personalize\EnableTransparency` en modo lectura. No crea claves, carpetas o respaldos, no guarda diarios ni reconcilia pendientes al consultar.
- **Estado:** DWORD 1 → Activada; DWORD 0 → Desactivada; ausencia u otro DWORD válido → Estado desconocido, sin inferir efecto visual. Un tipo incompatible bloquea cambios. Error de lectura → No disponible. Un respaldo inválido puede coexistir con un estado de Registro leído: se informa el error y se bloquean aplicar/restaurar.
- **Original:** el motor conserva el primer valor y su ausencia original. Aplicar de nuevo no reemplaza ese original. Restaurar una ausencia elimina únicamente el valor correspondiente mediante la frontera estable.
- **Diario:** se conserva intención persistida → comprobación de conflicto → escritura → lectura de confirmación → guardado de confirmación. Un fallo antes/después de escribir o guardar no se convierte en éxito. La UI muestra pendiente de reconciliación y ofrece las acciones compatibles; una restauración iniciada impide aplicar otro ajuste.
- **Conflictos:** se compara con Confirmed/Pending; un cambio externo no atribuible a JUNO bloquea aplicar/restaurar. El motor vuelve a comprobar inmediatamente antes de escribir. No se fuerza ni se ofrece sobrescribir desde la nueva UI.
- **Persistencia:** se reutilizan validación completa de General, límites/esquemas, identidad, migración histórica con revisión, copias history/previous/pending, validación de archivos y reemplazo atómico. Los campos de otros módulos se conservan.
- **Concurrencia:** ambas interfaces usan `Global\JUNO.0.8.State`. La antigua retiene el lease durante su sesión; la nueva lo adquiere por solicitud, incluida lectura de respaldos. Dos vistas pueden existir en reposo, pero no operan simultáneamente sobre el almacén. Recurso ocupado/inaccesible se informa sin intentar otra ruta.
- **Escrituras:** requieren confirmación tanto en el controlador como al entrar al proveedor/adaptador. No hay timeout, Kill, Stop o cancelación forzada de escrituras/restauraciones. El timeout de dashboard sigue limitado a su lector privado.
- **Resultado visual:** se distingue configuración solicitada, escritura confirmada en Registro, actualización visual pendiente, restauración completada, conflicto y fallo. Se conserva la notificación estable WM_SETTINGCHANGE tras una operación real autorizada; no se reinicia Explorer ni se cierra la sesión automáticamente.

## Procedimiento manual de validación real — pendiente del usuario

Este procedimiento incluye cambios de transparencia que **no se ejecutaron durante el desarrollo**. Repetir por separado en Windows 10 y Windows 11, con el mismo usuario durante aplicar/restaurar. Registrar edición/build, arquitectura de PowerShell, escala y resultado.

1. **Preparación y original.** Conservar juntos todos los scripts estables, archivos nuevos, ui/ y recursos. Guardar una copia de los respaldos existentes sin alterarlos. Consultar únicamente el original mediante `reg query "HKCU\Software\Microsoft\Windows\CurrentVersion\Themes\Personalize" /v EnableTransparency`; anotar tipo, valor o ausencia explícita. Registrar también la apariencia inicial.
2. **Apertura sin cambios.** Abrir `Abrir-Juno-Prototipo.cmd` como usuario normal. Revisar las cinco tarjetas de Inicio y actualizar manualmente. Visitar Rendimiento: debe leer transparencia y respaldo sin aplicar nada. Si aparece error de identidad, respaldo inválido, tipo incompatible o conflicto, detener la ronda de cambios y conservar los archivos para revisión. No borrar el respaldo para eludir el bloqueo.
3. **Navegación y cancelación.** Recorrer las seis secciones, redimensionar, desplazar contenido y volver a Rendimiento. Las otras herramientas siguen «Sin conectar». Pulsar Desactivar y cancelar la confirmación: comprobar que el valor y los respaldos permanecen iguales.
4. **Desactivación autorizada.** Solo con estado/respaldo válidos, pulsar Desactivar y Autorizar. Debe mostrarse solicitud en curso y luego escritura confirmada en Registro. Consultar de nuevo con reg query: debe ser REG_DWORD 0. Revisar que se conservó el original en el almacén estable; no editar JSON.
5. **Comprobación visual.** Observar superficies de Windows y la opción de transparencia en Configuración, sin tocar otros ajustes. Registrar si se actualizan, requieren reabrir una superficie o siguen pendientes. No interpretar «escritura confirmada» como prueba del efecto en todas las superficies. JUNO no debe reiniciar Explorer ni cerrar sesión.
6. **Activación autorizada.** Pulsar Activar y Autorizar. Debe confirmar REG_DWORD 1. El original guardado en el primer cambio no debe reemplazarse. Revisar nuevamente el efecto visual y cualquier diferencia de Windows 10/11.
7. **Restauración.** Desde Rendimiento, pulsar Restaurar original y Autorizar. Si existe un histórico sin diario, revisar Actual/Original y autorizar solo si corresponde. Debe verificarse exactamente el tipo/valor original o su ausencia, y quedar sin restauración de transparencia pendiente. Conservar las copias history/previous; no limpiarlas durante la prueba.
8. **Concurrencia.** Con la interfaz antigua abierta, consultar en la nueva: debe indicar recurso ocupado sin modificar nada. Cerrar la antigua y consultar otra vez. Para probar el sentido inverso durante una revisión histórica, usar una copia de prueba válida ya preparada y mantener la revisión abierta: la antigua debe rechazar adquirir el recurso. No fabricar una interrupción cerrando el proceso durante una escritura; esos fallos ya tienen pruebas simuladas.
9. **Cierre y ausencia de cambios inesperados.** Comprobar navegación durante una lectura y cierre normal. Durante una escritura corta, si se alcanza a cerrar, debe pedir esperar su verificación. Comparar el original/restaurado, los campos de otros módulos en el respaldo y los ajustes observados antes/después. No activar herramientas ajenas a Transparencia. Si hay conflicto, fallo o resultado desconocido, guardar el mensaje y los diarios y detenerse.
10. **Matriz.** Repetir en Windows 10/11 Home/Pro disponibles, y PowerShell 5.1 x86/x64 en sistemas de 64 bits. Para abrir explícitamente x86 usar `C:\Windows\SysWOW64\WindowsPowerShell\v1.0\powershell.exe -NoProfile -STA -ExecutionPolicy Bypass -File "C:\GitHub\Juno\Juno-Prototipo.ps1"`. No cambiar DPI, políticas o permisos del equipo como parte de esta ronda.

## Compatibilidad y limitaciones

- Implementación para Windows PowerShell 5.1, C#/.NET Framework y WinForms. Usa System.Management.Automation del propio host; no añade paquetes ni otra tecnología. En un Windows de 32 bits solo corresponde x86.
- Se verificaron compilación y simulaciones en x86/x64 sobre el equipo Windows 11 disponible. La matriz manual completa de Windows 10/11 Home/Pro y escrituras reales queda pendiente.
- La configuración de Registro no certifica el efecto visual. El sistema, sesión y superficies pueden actualizarse de forma diferente. No se automatiza reinicio de Explorer o sesión.
- Un respaldo inválido o vinculado a otra identidad impide operaciones. No se añadió una herramienta para reparar/descartar respaldos. Los conflictos externos se conservan para revisión; no hay opción nueva para forzarlos.
- El cierre en lectura deja terminar el runspace en segundo plano. Las operaciones locales no tienen plazo forzado: un bloqueo del proveedor o sistema puede requerir esperar. Durante escritura, el cierre normal se difiere; cierre forzado del proceso, caída o apagado pueden dejar un diario pendiente que debe reconciliarse en la próxima operación.
- Al restaurar una ausencia se restaura la ausencia del **valor**; no se promete eliminar una clave que pudo crearse. Esto conserva el comportamiento estable.
- Las pruebas geométricas y renders no certifican DPI real 100/125/150/200 %, monitores mixtos, lector de pantalla o alto contraste. No se cambió la estrategia DPI existente.
- El bloqueo coordina instancias de JUNO, no herramientas externas que ignoren el mutex. El motor comprueba conflictos antes y después de sus fronteras, sin prometer atomicidad global con todos los procesos de Windows.
