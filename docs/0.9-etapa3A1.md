# JUNO v0.9 — Etapa 3A.1: identidad y validación de respaldos

Fecha: 18/10/2026. Rama: `feature/juno-ui-0.9`. Sin commit de Etapa 3A ni 3A.1.

## 1. Causa exacta reproducida

**El respaldo local examinado es válido en la sesión normal. El rechazo anterior se produjo al leerlo desde el sandbox de herramientas, cuyo token tiene una identidad de usuario diferente.** La comparación que falló fue exclusivamente el SID de usuario del sobre frente a `WindowsIdentity.GetCurrent().User.Value`.

Fuera del sandbox, **sin elevación**, el mismo archivo pasa la validación directa y la consulta del adaptador C#/PowerShell tanto en x64 como en x86. No se corrigieron sus datos ni se migró su identidad. El bloqueo sigue siendo obligatorio cuando la identidad de la ejecución no coincide.

La explicación genérica anterior agrupaba usuario/equipo/módulo/ámbito y no permitía atribuir el rechazo. Esta etapa corrige ese diagnóstico. No se sustituye la identidad del token por el nombre de una carpeta, variables de entorno, el propietario de un perfil o el SID escrito en el propio respaldo.

## 2. Evidencia técnica sin datos personales

El documento inspeccionado es el almacén lógico **General / User**, archivo `backup.json` en el directorio de datos de JUNO del usuario. No se publican su ruta expandida, SID, identificador de equipo, revisión, contenido ni huellas.

La elegibilidad de botones **no prueba una escritura o restauración real**: no se solicitaron esas operaciones. El estado actual de transparencia solo se consultó.

Las primeras consultas x64/x86 lanzadas simultáneamente produjeron una lectura y un rechazo Busy. Repetir x86 secuencialmente devolvió Read. Es el comportamiento esperado del mutex, no una incompatibilidad de arquitectura.

### Identidad y ámbitos

`Get-JunoIdentity` conserva su implementación: lee MachineGuid mediante la vista nativa Registry64 en un Windows de 64 bits y obtiene el SID del token con WindowsIdentity. No usa una vista de equipo distinta por ejecutar PowerShell x86. El GUID de equipo conserva su comparación sin sensibilidad a mayúsculas; el SID mantiene la comparación estricta existente.

Transparencia utiliza exclusivamente HKCU y el almacén General/User. Leer MachineGuid en HKLM identifica el equipo; **no convierte la operación de transparencia en una operación HKLM**. Scope Machine y sus ACL continúan separados.

El diagnóstico observado no fue un problema de elevación: ambas ejecuciones medidas fueron no elevadas. Se simulan por separado el mismo usuario con distintos privilegios y una cuenta diferente con privilegios. No se ejecutó una prueba UAC real. La API representa la identidad de la ejecución, y UAC diferencia token estándar/administrativo; no debe usarse la elevación como sustituto de identidad. Referencias: [WindowsIdentity.GetCurrent](https://learn.microsoft.com/en-us/dotnet/api/system.security.principal.windowsidentity.getcurrent?view=netframework-4.8.1) y [funcionamiento de UAC](https://learn.microsoft.com/en-us/windows/security/application-security/application-control/user-account-control/how-it-works).

### Hipótesis descartadas y pendientes

- **Descartadas para este documento:** histórico sin identidad, equipo diferente, ámbito equivocado, esquema incompleto, versión incompatible y fallo del puente nuevo. Las comparaciones y las lecturas normales lo demuestran.
- **Confirmado:** identidad de ejecución distinta dentro del aislamiento y diagnóstico genérico insuficiente.
- **Pendiente:** comportamiento real elevado, otras cuentas/equipos y matriz completa Windows 10/11. Las variantes se prueban con dependencias ficticias, no se confunden con verificaciones reales.
- No se identifica ni atribuye el SID del sandbox a una persona, ni se infiere la autoría histórica de otros archivos.

## 3. Corrección implementada

### Diagnóstico compartido y seguro

En `BackupStore.ps1` se separaron las condiciones del rechazo combinado, **sin relajar sus comparaciones**. Los errores transportan un código estable en Exception.Data:

| Código | Significado |
| --- | --- |
| UserMismatch | SID del respaldo diferente al de esta ejecución |
| MachineMismatch | Equipo diferente |
| ScopeMismatch | Ámbito incompatible o SID de usuario en un sobre Machine |
| KindMismatch | Otro módulo |
| FormatMismatch | Formato incompatible |
| UnverifiableLegacy | General histórico sin identidad verificable |
| InvalidBackup | Lectura/esquema/versión no válidos u otro rechazo no clasificable |

El envoltorio de lectura conserva ese código a través de excepciones de PowerShell/.NET. Los mensajes de presentación no interpolan rutas, SID, identificador de equipo, JSON ni detalles privados de errores del sistema.

`TransparencyAdapter.ps1` reutiliza esos códigos y mensajes. Mantiene separado el estado leído de Windows de la posibilidad de aplicar/restaurar. Por ejemplo, «Activada» puede coexistir con un error de identidad y controles bloqueados. El DTO C# incorpora `BackupIssue`; no se cambió el diseño ni se copió lógica de restauración a C#.

### Históricos sin identidad

La revisión del lector mostró una vía adicional relevante para el requisito de procedencia: un **General sin sobre** era aceptado por su forma de datos, aunque no pudiera demostrar usuario ni equipo. Una confirmación visual de Actual/Original no demuestra por sí sola esa procedencia.

Ahora ese documento queda bloqueado por el lector compartido, también si se solicita `-Legacy`. No se inventa una migración, no se captura el estado actual como original y no se permite que una copia history/previous sin identidad se convierta automáticamente en autoridad.

Se mantiene la compatibilidad con **JUNO.Backup v1 identificado**, incluido un Data antiguo sin diario. Si contiene un original pero no un diario atribuible, el motor sigue pidiendo su revisión adicional antes de aplicar/restaurar. El archivo anterior se conserva mediante el protocolo de reemplazo y copias previous existente.

El alcance de esta restricción es **General**, que comparten transparencia, efectos y antiguos datos generales. Por ello un General antiguo sin identidad también deja de ser aceptado por rutas antiguas que lo consumían. Los formatos específicos de otros módulos no se rediseñaron ni se integraron; su revisión corresponde a sus etapas.

## 5. Conservación y garantías de integración

- Ningún respaldo real se eliminó, editó, sobrescribió o trasladó. No se cambiaron permisos.
- Se tomaron huellas de los JSON de datos existentes bajo el mutex, solo para comparación en memoria, sin guardar copias personales en el repositorio.
- No se ejecutaron activación/desactivación/restauración reales, notificación WM_SETTINGCHANGE, optimización, reinicio de Explorer ni cierre de sesión.
- El motor estable continúa guardando el primer original y su ausencia, persistiendo intención, comprobando conflictos, escribiendo, releyendo y confirmando.
- Permanecen recuperación de operaciones parciales, restauración pendiente, bloqueo ante cambios externos y exclusión entre interfaces/procesos.
- El adaptador mantiene un runspace propietario del lease y no aplica timeouts ni cancelación forzada a escrituras.
- Rechazar un documento no permite iniciar una operación nueva con un original inventado. La ausencia del archivo principal con copias recuperables sigue siendo un bloqueo.

La comparación final bajo el mutex confirmó que los **16 archivos JSON existentes permanecen idénticos por SHA-256** respecto de la instantánea inicial. Las huellas y nombres de archivo se mantuvieron únicamente en memoria y no se publican.

## 6. Pruebas

La suite integral final aprobó **465/465 pruebas en x64 y 465/465 en x86** (930 ejecuciones), con Windows PowerShell **5.1.22621.6133** y Pester **3.4.0**. Los **28 archivos PowerShell** pasaron el análisis de sintaxis en ambas arquitecturas. C# de producción y fixtures compiló en procesos nuevos. `git diff --check`, revisión de espacios finales e índice vacío: correctos. La comparación por AST verificó sin cambios Get-JunoIdentity, Test-JunoAdmin, Enter-JunoLease, Assert-JunoLease, Exit-JunoLease y Write-JunoStore.

Se conservan los **441 casos** de Etapa 3A, con tres adaptaciones justificadas: el caso General sin identidad pasa a exigir rechazo, y los dos casos de revisión histórica del puente usan documentos v1 identificados. Estos últimos siguen verificando confirmación, cancelación, conservación byte a byte y restauración de ausencia; la conservación del documento identificado se comprueba en previous.

Se agregan **24 casos**: 18 del almacén/identidad y 6 de puente/UI. Cubren usuario correcto, otro usuario, otro equipo, mismo usuario normal/elevado simulado, otra identidad elevada, diferencia User/Machine, formato/módulo incorrectos, documento incompleto, JSON inválido, versión futura, histórico identificado sin diario, General sin identidad incluso con Legacy, recuperación de una copia sin identidad, mensajes sin datos privados y códigos en excepciones anidadas.

Las pruebas del puente comprueban el rechazo antes de activar/desactivar/restaurar, bytes intactos, consulta de Windows disponible aunque el respaldo esté bloqueado, ausencia de revisión como atajo para un histórico no verificable y reintento con un token ficticio correcto **sin cambiar la identidad del documento**. La tarjeta permite consultar, pero no confirmar ni enviar escrituras ante UserMismatch.

Las suites anteriores siguen cubriendo activación/desactivación/restauración simuladas, originales ausentes, fallos de persistencia/escritura/lectura, restauración parcial, conflictos externos, reintentos, concurrencia entre procesos, confirmaciones y apertura/cierre/navegación sin modificaciones de Windows.

Los archivos e identidades de pruebas son ficticios. Las barreras de los fixtures impiden llegar al Registro, notificaciones, identidad o respaldos reales. Los procesos de prueba utilizan mutex Local únicos y TestDrive.

### Reproducir

En procesos nuevos de PowerShell 5.1, desde el repositorio:

```powershell
$test = {
    $ErrorActionPreference='Stop'
    $ProgressPreference='SilentlyContinue'
    Import-Module Pester -RequiredVersion 3.4.0
    $r=Invoke-Pester -Script .\tests -Quiet -PassThru
    $r | Select-Object TotalCount,PassedCount,FailedCount
    if($r.FailedCount){exit 1}
}
& "$env:WINDIR\System32\WindowsPowerShell\v1.0\powershell.exe" -NoProfile -NonInteractive -STA -ExecutionPolicy Bypass -Command $test
& "$env:WINDIR\SysWOW64\WindowsPowerShell\v1.0\powershell.exe" -NoProfile -NonInteractive -STA -ExecutionPolicy Bypass -Command $test
```

No reutilizar sesiones con una versión anterior de los tipos C# ya cargada.

## 7. Validación manual posterior

### Lectura, identificación y bloqueo

1. Usar la sesión normal del usuario de origen. Abrir `Abrir-Juno-Prototipo.cmd` sin «Ejecutar como otro usuario». No recurrir a UAC para intentar resolver un SID distinto.
2. Visitar Rendimiento y consultar Transparencia. En el documento examinado aquí debe poder leer estado/respaldo; no hay reparación o migración que ejecutar.
3. Si otro entorno informa UserMismatch, comprobar la identidad **del contexto de ejecución** de forma local, sin enviar identificadores completos. No editar Sid, Machine o Scope del JSON para hacerlos coincidir.
4. Verificar que el mensaje diferencia identidad, equipo, ámbito o documento no verificable. «Consultar estado» debe seguir disponible; aplicar/restaurar deben permanecer bloqueados cuando no haya recuperación segura.
5. Conservar originales y copias existentes. Comparar huellas antes/después de abrir y consultar, sin publicar rutas privadas ni contenido.
6. No provocar incompatibilidades cambiando respaldos reales. Para ver la tarjeta bloqueada y probar otros usuarios/equipos, usar los fixtures automatizados o un entorno desechable con datos ficticios.

Una comprobación de solo lectura y sin salida del contenido, con la aplicación cerrada, puede ejecutarse desde una consola normal situada en el repositorio:

```powershell
. .\BackupStore.ps1
$script:AppFolder=Join-Path $env:LOCALAPPDATA 'WinRendimiento'
Enter-JunoLease
try {
    [void](Read-JunoStore General User $null)
    'Validación aceptada o almacén aún inexistente.'
}
catch {
    'Validación rechazada: '+(Get-JunoBackupFailureCode $_.Exception)
}
finally { Exit-JunoLease }
```

No exportar el ErrorRecord completo ni imprimir el JSON/identificadores para un informe público.

### Recuperación supervisada de un histórico realmente no verificable

1. Detener cambios/restauraciones y conservar el bloqueo. Respaldar la evidencia fuera de los archivos activos, preservando bytes y huellas; no renombrar/eliminar el principal para que JUNO lo considere vacío.
2. Revisar **copias aisladas** con una persona que pueda acreditar usuario, equipo, origen, ámbito y originales. Un JSON bien formado, una ruta conocida, el propietario de la carpeta o una confirmación visual no acreditan por sí solos esos datos.
3. Buscar una copia existente identificada y compatible del mismo almacén/ámbito. Validarla bajo la identidad de origen y reconciliar su diario con el estado real antes de considerar una recuperación.
4. No trasplantar SID/Machine de otro documento ni envolver automáticamente los datos antiguos con la identidad actual. No trasladar respaldos de usuario al almacén administrativo ni al revés.
5. Si no existe evidencia suficiente, **no restaurar a partir de ese histórico**. Documentar la falta de procedencia y mantener bloqueado el módulo hasta una decisión supervisada y autorizada; esta etapa no incorpora una herramienta de descarte, reparación o migración.
6. Cualquier recuperación de archivos activos o modificación de Windows corresponde a una autorización posterior. Aquí no se ejecutó ninguna.

### Restauración real válida, solo cuando se autorice

Con respaldo identificado y compatible, registrar primero estado original y ausencia/tipo/valor. Autorizar un único cambio de transparencia en un entorno de prueba, comprobar escritura y efecto visual por separado, y restaurar desde Rendimiento. Confirmar que vuelve exactamente el original o su ausencia y que no se reemplazó por el estado observado al reintentar. Conservar los diarios/copias; detenerse ante conflicto o resultado desconocido.

La matriz manual pendiente incluye Windows 10/11, PowerShell x86/x64, cuenta normal y elevación real de la misma cuenta. No se simulan fallos interrumpiendo escrituras reales ni alterando políticas, permisos o servicios.

## 8. Riesgos pendientes y continuación

- Las comprobaciones reales realizadas fueron de lectura sobre el Windows 11 disponible. No certifican cambios reales, Windows 10 ni UAC real.
- Los metadatos vinculados y el esquema validado no son una firma criptográfica de autoría. Se conserva el modelo de confianza existente y no se promete autenticar archivos manipulados por quien ya pueda escribirlos.
- General sin identidad queda deliberadamente más restringido, también en la interfaz antigua. La recuperación supervisada no tiene un atajo automático.
- Los errores genéricos de E/S se presentan sin detalles privados; el diagnóstico técnico adicional debe hacerse localmente sobre copias, sin publicar datos personales.
- No se extendió la revisión a formatos específicos de los demás módulos ni se integró ninguno nuevo.
- Continuar primero con pruebas manuales de lectura en la sesión normal. No reparar el respaldo válido examinado. Después, revisar esta etapa antes de autorizar modificaciones reales o conectar otra herramienta.
