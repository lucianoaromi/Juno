# JUNO v0.9 — Etapa 2: interfaz y dashboard real

## A. Mejoras implementadas

Se conserva el diseño aprobado: tema oscuro, menú lateral, gato original, Segoe UI, acento dorado y tarjetas. Inicio muestra ahora una colección real de lecturas de Windows. Se retiraron los valores simulados y el bloque de bienvenida redundante para dar espacio a la información. Se ajustaron tamaño de valores, padding y separaciones de tarjetas, conservando etiquetas que crecen con su contenido y distribución en columnas según el ancho.

El título de Rendimiento es **«Configuración de rendimiento»**. Las seis secciones siguen dentro del mismo formulario. Las herramientas y restauraciones muestran **«Pendiente de integración»** y botones **«Sin conectar»** deshabilitados. Ningún estado de optimización se presenta como comprobado. Se preparó un vocabulario de presentación para Disponible, Requiere administrador, No compatible, Estado desconocido y Pendiente de integración; las herramientas actuales usan exclusivamente este último.

Inicio realiza una consulta al mostrarse por primera vez. Después se actualiza solo mediante **«Actualizar información»**. La navegación no inicia consultas nuevas. Un mensaje discreto informa carga, lectura completa/parcial, hora de finalización o timeout. El botón cambia a «Actualizando información…» y a un color atenuado mientras está deshabilitado. Cada tarjeta diferencia datos disponibles, parciales y ausentes. El refresco muestra la instantánea anterior claramente identificada hasta recibir la nueva; un fallo final sustituye los datos faltantes por **«No disponible»**, sin conservarlos como si fueran nuevos.

## C. Arquitectura y ciclo del dashboard

```text
Juno-Prototipo.ps1
  → ShellForm → DashboardController (estado, caché, una tarea)
                   → IDashboardQuery / ProcessDashboardQuery
                       → proceso privado Windows PowerShell 5.1
                           → Juno-DashboardWorker.ps1
                               → DashboardCollector / WindowsReadApi
                       ← JSON por categoría, sin controles ni comandos
                   ← DashboardSnapshot
              ← timer WinForms recoge tarea terminada y actualiza la vista
```

El constructor de controles no consulta hardware. El bootstrap inyecta el proveedor real; el constructor de vista sin proveedor se usa para construcción aislada y presenta datos ausentes, nunca valores de ejemplo. `LoadOnly` compila tipos y no abre ni consulta el dashboard.

`DashboardController` admite solo una solicitud pendiente. Una segunda solicitud durante la carga devuelve false. Navegar conserva el controlador y su instantánea; se dispone únicamente la página anterior. El timer WinForms de 100 ms funciona solo mientras se recoge la consulta y se detiene al terminar. No existe monitor periódico de memoria/CPU. Los eventos de stdout trabajan sobre datos protegidos por un lock, sin referencias a controles. La UI obtiene el resultado solo después de `Task.IsCompleted`, por lo que no espera a WMI ni a procesos desde su hilo.

El trabajador publica primero RAM, unidad y energía; después las dos categorías WMI. Una excepción de categoría no impide intentar las demás. El protocolo admite solo las cinco categorías, limita tamaño/profundidad y detecta salida inválida o duplicada. No admite órdenes de aplicar/restaurar ni parámetros de comandos del usuario.

WMI tiene un timeout de enumeración de 3 segundos. Este no garantiza limitar la conexión o un proveedor bloqueado; por eso hay un límite independiente de **15 segundos desde el inicio del trabajador**, incluyendo su compilación. Al excederlo se termina únicamente ese proceso privado y se conservan las respuestas ya recibidas. La espera de liberación y vaciado de canales puede añadir unos segundos; se realiza fuera del hilo UI. Si Windows impide finalizar el trabajador, esa instancia del proveedor rechaza crear otros para evitar acumulación.

Cerrar el formulario detiene/dispone el timer y cancela la tarea. El supervisor recibe la cancelación y libera su propio trabajador, streams, handles y eventos; la cancelación no ejecuta callbacks sobre controles. La disposición del controlador es idempotente y no bloquea el cierre esperando consultas. Buffers de energía, objetos WMI, icono clonado, fuentes y recursos de dibujo se disponen en sus ámbitos correspondientes.

## D. Consultas oficiales y significado de los valores

| Tarjeta | Lectura | Presentación y límites |
| --- | --- | --- |
| Windows | `SELECT Caption,Version,BuildNumber,OSArchitecture FROM Win32_OperatingSystem` | Caption incluye nombre y edición instalada; versión, build y arquitectura se presentan por separado. La arquitectura es la del sistema, no la del proceso PowerShell. No se inventa una edición a partir de la build. |
| CPU | `SELECT Name,NumberOfCores,NumberOfLogicalProcessors FROM Win32_Processor` | Conserva modelos reportados y suma los contadores de todas las instancias. Un contador ausente/0 no se transforma en un núcleo válido. Es lo que expone Windows/firmware/VM, no una certificación física. |
| RAM | `GetPhysicallyInstalledSystemMemory` y `GlobalMemoryStatusEx` | Muestra instalada, disponible y porcentaje sobre RAM utilizable por Windows. Instalada y utilizable pueden diferir por reservas de hardware. Los contadores son UInt64 también en x86. |
| Almacenamiento | Raíz de `Environment.SpecialFolder.Windows`; `DriveInfo.Name`, `IsReady`, `TotalSize`, `TotalFreeSpace` | Solo el volumen donde está Windows. Disponible significa libre total del volumen, no cuota personal ni suma de discos físicos. No se infiere SSD/HDD ni salud de esa lectura. |
| Energía | `PowerGetActiveScheme` y `PowerReadFriendlyName` | Nombre localizado del plan activo, disponible o desconocido. Se libera el GUID con `LocalFree`. No se llama a ninguna API de cambio de plan ni a `powercfg`. |

Los tamaños usan unidades binarias **GiB/TiB**, explícitamente. El porcentaje es `100 × (total − disponible) / total`, redondeado a una decimal. En RAM, el denominador es la memoria utilizable; en almacenamiento, el tamaño del volumen. Total cero, número ausente/malformado o disponible mayor que total produce **«No disponible»**, nunca 0 %. Un disponible real de cero sigue siendo válido y puede producir 100 %.

Las cinco lecturas se toman durante una ronda; no son simultáneas. La hora mostrada corresponde a finalización de la ronda. RAM y espacio libre pueden cambiar inmediatamente después; volver a una sección no los actualiza automáticamente.

Referencias: [Win32_OperatingSystem](https://learn.microsoft.com/en-us/windows/win32/cimwin32prov/win32-operatingsystem), [Win32_Processor](https://learn.microsoft.com/en-us/windows/win32/cimwin32prov/win32-processor), [memoria instalada](https://learn.microsoft.com/en-us/windows/win32/api/sysinfoapi/nf-sysinfoapi-getphysicallyinstalledsystemmemory), [MEMORYSTATUSEX](https://learn.microsoft.com/en-us/windows/win32/api/sysinfoapi/ns-sysinfoapi-memorystatusex), [espacio libre del volumen](https://learn.microsoft.com/en-us/dotnet/api/system.io.driveinfo.totalfreespace?view=netframework-4.8.1), [plan activo](https://learn.microsoft.com/en-us/windows/win32/api/powersetting/nf-powersetting-powergetactivescheme), [nombre del plan](https://learn.microsoft.com/en-us/windows/win32/api/powrprof/nf-powrprof-powerreadfriendlyname) y [opciones WMI/alcance de timeout](https://learn.microsoft.com/en-us/dotnet/api/system.management.enumerationoptions?view=netframework-4.8.1).

No hay escrituras de Registro, políticas, servicios, permisos, configuración, archivos personales ni respaldos. No se enumeran o cierran procesos de aplicaciones. Solo se crean/terminan procesos privados del lector y de pruebas. `Add-Type` puede usar temporales de compilación normales del host; no se genera un ejecutable final, instalador o dependencia visual adicional. El navegador solo se abre si el usuario pulsa el enlace de GitHub ya existente.

## F. Compatibilidad

Se conserva Windows PowerShell 5.1, C# del compilador de .NET Framework y WinForms existentes. `System.Management` y `System.Web.Extensions` pertenecen a .NET Framework; no se agregan bibliotecas externas ni otra tecnología. El trabajador usa el `powershell.exe` de `$PSHOME`, de la misma arquitectura del lanzador. No solicita `runas`, privilegios administrativos ni cambios persistentes de política de ejecución.

Las API de memoria/energía seleccionadas existen desde versiones anteriores a Windows 10. Se manejan sus fallos y la ausencia/restricción de WMI. La implementación es compatible por diseño con Windows 10/11 Home/Pro; **la matriz real completa sigue pendiente**. Una cuenta/política/VM puede limitar qué datos devuelve el proveedor y eso debe mostrarse como desconocido, no resolverse elevando automáticamente.

La estrategia DPI sigue siendo la de Etapa 1: system-aware, medidas según DPI inicial y fuentes en puntos, sin mezclar escalado manual/automático. Se mantienen columnas adaptables, texto envuelto y desplazamiento. Las pruebas geométricas y renders no certifican 100/125/150/200 % reales, fuentes ampliadas, monitores mixtos, PerMonitorV2 ni accesibilidad completa.

## G. Limitaciones conocidas

- La compilación inicial y un trabajador PowerShell por refresco tienen un coste de arranque. Se prioriza aislar bloqueos de proveedores y dejar cero sondeos de hardware cuando la vista está inactiva. No se midió un benchmark de consumo.
- El límite externo protege frente a proveedores que no respeten el timeout WMI. La cancelación/finalización del trabajador y la disposición pueden tardar; ocurren fuera del hilo UI. No se cancelan ni terminan procesos de aplicaciones del usuario.
- La instantánea es de memoria: no se persiste entre aperturas y no constituye monitoreo continuo. Una lectura parcial puede omitir nombre/edición/arquitectura o contadores; no se rellenan con supuestos.
- El panel de almacenamiento describe el volumen de Windows, no todos los discos, cuotas, SMART, TRIM físico o recuperación de espacio.
- Los estados de herramientas son estructura visual futura. No se ha comprobado elegibilidad, permisos ni eficacia de optimizaciones desde esta interfaz.
- Quedan pendientes validaciones manuales de teclado, lector de pantalla, alto contraste, sistemas/ediciones adicionales, DPI real y movimiento entre monitores. Los widgets conservan nombres/foco básicos; eso no acredita accesibilidad completa.

## H. Cómo probar la interfaz

1. Abrir `Abrir-Juno-Prototipo.cmd` como usuario normal, conservando juntos `Juno-Prototipo.ps1`, `Juno-DashboardWorker.ps1`, los cuatro `.cs` de `ui/` y `Juno.ico`. No usar el trabajador como entrada principal.
2. En Inicio, observar carga y navegar inmediatamente a otra sección. Debe seguir respondiendo sin abrir otra ventana. Volver a Inicio y leer la instantánea completa/parcial. No debe reiniciar la consulta por navegar.
3. Comparar nombre/edición/build/arquitectura con Acerca de de Windows; CPU/contadores/RAM con información del sistema; capacidad/libre con propiedades del volumen; nombre del plan con el panel de energía. Abrir esos paneles solo para leer y cerrarlos sin aplicar nada. No exigir coincidencia instantánea de memoria libre ni mezclar GB con GiB.
4. Pulsar «Actualizar información». Debe deshabilitarse mientras carga, marcar valores anteriores si los hay y permitir seguir navegando. Esperar la nueva lectura y comprobar que se habilita de nuevo. No debe refrescarse continuamente.
5. Recorrer las seis secciones, revisar selección, rótulo de Rendimiento y estados. Todos los botones de aplicar/restaurar permanecen sin conectar. No ejecutar la versión estable para comprobar cambios durante esta ronda.
6. Redimensionar, maximizar, usar Tab y barras de desplazamiento. Probar otras escalas solo en entornos ya preparados; cambiar el DPI del equipo queda fuera de esta prueba de lectura.
7. Cerrar durante una carga y volver a abrir. Registrar error, espera, sistema/build, arquitectura, escala y pasos si la ventana deja de responder. Para probar fallos/timeout, usar los fixtures automatizados; no deshabilitar WMI, servicios o políticas de un equipo real.

Para ver errores de arranque: `powershell.exe -NoProfile -STA -ExecutionPolicy Bypass -File "C:\GitHub\Juno\Juno-Prototipo.ps1"`. No hay reinicio, elevación automática ni conexión con módulos de escritura.

Reproducir suites en procesos nuevos de cada arquitectura, desde el repositorio:

## J. Recomendaciones para la Etapa 3

Integrar cada herramienta por un adaptador hacia las funciones existentes, con identificadores únicos de operación separados de los iconos. Mantener diferenciadas capacidad/disponibilidad, lectura, confirmación, solicitud, escritura, validación y eficacia. No reutilizar el trabajador de dashboard para escrituras ni darle acceso a los diarios o al mutex propietario de las transacciones.

Las operaciones estables deben conservar sus guardas de usuario/equipo, administrador, compatibilidad, originales, conflictos, diarios y revalidación. Convertir diálogos en vistas insertables gradualmente, sin copiar la lógica al shell. Antes de habilitar cada botón, definir su contrato de estado, cancelación aplicable y prueba aislada; el timeout lector no autoriza interrumpir una escritura/restauración. La compatibilidad con históricos debe seguir probándose y las pruebas reales de modificación requieren autorización separada.

Esta etapa termina con dashboard lector y herramientas pendientes de integración. El trabajo se detiene para revisión.
