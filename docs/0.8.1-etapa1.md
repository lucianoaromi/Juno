# JUNO 0.8.1 — Etapa 1: recuperación de operaciones

Implementación local sobre `fix/auditoria-0.8.1`. Alcance: Inicio y permisos
de segundo plano por usuario. No se modifican energía, limpieza, discos,
directivas de equipo, iconos ni la organización de la interfaz.

## Inicio

Se conserva el estado original (`OriginalExists` / `OriginalData`). Cada registro
incorpora un diario aditivo `Transaction`, con versión, estado `Confirmed` y
escritura `Pending`. `LastWrittenData` solo representa una escritura de aplicación
verificada; ya no almacena una intención antes de ejecutarla.

Antes de escribir se guarda la intención y se relee el valor. Después se comparan
los bytes completos, no solo el indicador activo/desactivado. Solo entonces se
guarda la confirmación. Si una escritura, lectura o guardado falla, el siguiente
intento puede reconocer el último valor confirmado o el destino pendiente.
Un tercer valor provoca un conflicto y no se sobrescribe.

La restauración utiliza el mismo protocolo, incluida la ausencia original del
valor. Si ya se restauró y el proceso terminó antes de actualizar el JSON,
el siguiente intento puede completar la operación sin repetir la escritura.

## Permisos por usuario

Se mantienen `Version=1`, `Sid` y los valores originales `Disabled` y
`DisabledByUser`. El diario adicional guarda `Confirmed` / `Pending` por DWORD
y la fase `Applying`, `Applied` o `Restoring`.

Cada escritura o eliminación se guarda como pendiente, se ejecuta y se relee
individualmente. La fase solo pasa a `Applied` después de verificar ambos DWORD.
Una restauración parcial conserva el progreso confirmado y puede reanudarse.
No se permite iniciar otro bloqueo mientras exista una restauración pendiente.

La ventana existente permite reintentar un bloqueo pendiente y muestra el
respaldo como cambio que requiere verificación. No se afirma que los valores
registrados demuestren una restricción efectiva de actividad en segundo plano.

## Respaldos anteriores

Los campos originales se conservan. No se eliminan los archivos anteriores.
Como en el flujo previo, las entradas completadas se retiran del JSON solo
después de verificar su restauración; las entradas pendientes se conservan.

En Inicio, el antiguo `LastWrittenData` se interpreta como intención. Para cada
DWORD de permisos antiguo se admite el original o el destino conocido `1`.
Esto permite recuperar fallos completos y parciales de v0.8. Si el valor es
distinto de ambas posibilidades se detiene la operación.

La migración no puede reconstruir un historial que v0.8 nunca guardó: un cambio
externo que coincida exactamente con el original o el destino pendiente es
indistinguible de esos estados. No se deben alternar versiones antiguas de JUNO
con estos cambios pendientes.

## Pruebas y reproducción

Se utiliza el Pester 3.4.0 instalado, sin dependencias nuevas. Las pruebas
importan únicamente las funciones seleccionadas mediante AST. Las funciones
que abrirían el Registro se sustituyen por barreras que arrojan error y por
objetos de memoria; nunca se ejecutan los módulos completos ni la GUI.
Las pruebas de archivos usan exclusivamente el `TestDrive` temporal de Pester.

Desde la raíz del repositorio:

```powershell
powershell.exe -NoProfile -NonInteractive -ExecutionPolicy Bypass -Command 'Import-Module Pester -RequiredVersion 3.4.0; $r = Invoke-Pester -Script ".\tests\Recovery.Tests.ps1" -PassThru; if ($r.FailedCount -gt 0) { exit 1 }'
```

El parámetro de política afecta únicamente al proceso de prueba. No se cambia
la política persistente del equipo. Para x86 se utiliza el mismo comando con
`%WINDIR%\SysWOW64\WindowsPowerShell\v1.0\powershell.exe`.

La suite cubre aplicación completa, fallo antes y después de cada escritura,
escrituras no conservadas, errores de guardado en cada punto, reintentos,
restauración completa/parcial, conflictos externos, idempotencia, valores
originalmente ausentes, respaldos antiguos y preservación de entradas ajenas.

Resultado: 75 pruebas en Windows PowerShell 5.1.22621.6133, tanto x64 como x86.
Análisis sintáctico y `git diff --check` sin errores.

## Límites y pendientes fuera de esta etapa

- Validar en máquinas virtuales Windows 10/11 Home/Pro: ACL, UAC, formatos de
  StartupApproved y flujo de botones. Las pruebas aisladas no certifican estos
  entornos ni la eficacia de los indicadores de segundo plano.
- Los JSON siguen usando la persistencia existente: faltan bloqueos entre
  instancias, historial de versiones y endurecimiento frente a manipulación.
- Comparar, guardar y escribir no constituye un compare-and-swap atómico del
  Registro. Una carrera con otra herramienta puede ocurrir entre comprobaciones;
  tampoco puede identificarse el autor de un valor idéntico al esperado.
- La validación exhaustiva de destinos y esquemas de respaldo, la detección
  MDM/Entra, los cambios de ámbito usuario/equipo y la recuperación desde la GUI
  de aplicaciones desinstaladas quedan pendientes según la auditoría.
- No se ejecutaron cambios reales del sistema, optimizaciones, commits ni push.
